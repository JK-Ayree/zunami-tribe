# F14 — Alerts API Contract

## 1. Назначение

API предназначен для получения и управления уведомлениями о проблемах с хостами.

Уведомления создаются автоматически:
- при нарушении включённого правила F8;
- при недоступности хоста более 30 секунд.

Статусы:
- `firing` — активное уведомление;
- `resolved` — решённое уведомление.

## 2. Получение уведомлений

`GET /api/alerts`

Возвращает все уведомления.

Можно использовать фильтр по статусу:

- `GET /api/alerts?status=firing` — активные;
- `GET /api/alerts?status=resolved` — решённые.

Успешный ответ: HTTP `200 OK`

```json
{
  "items": [
    {
      "id": 1,
      "host_id": 1,
      "host_name": "lab-server-01",
      "rule_id": 2,
      "kind": "threshold",
      "status": "firing",
      "message": "CPU выше установленного порога: 85% (порог 80%)",
      "severity": "high",
      "started_at": "2026-11-27T15:00:00Z",
      "resolved_at": null
    },
    {
      "id": 2,
      "host_id": 2,
      "host_name": "lab-server-02",
      "rule_id": null,
      "kind": "offline",
      "status": "firing",
      "message": "Хост недоступен более 30 секунд",
      "severity": "high",
      "started_at": "2026-11-27T15:01:00Z",
      "resolved_at": null
    }
  ],
  "total": 2
}
```

Если уведомлений нет:

```json
{
  "items": [],
  "total": 0
}
```

## 3. Поля уведомления

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | ID уведомления |
| `host_id` | integer | ID хоста |
| `host_name` | string | Название хоста |
| `rule_id` | integer или null | ID правила F8, если уведомление связано с правилом |
| `kind` | string | Тип уведомления |
| `status` | string | Статус уведомления |
| `message` | string | Описание проблемы |
| `severity` | string | Важность |
| `started_at` | string | Время возникновения |
| `resolved_at` | string или null | Время решения |

Допустимые значения `kind`:
- `threshold` — нарушение правила мониторинга;
- `offline` — хост недоступен.

Допустимые значения `severity`:
- `low`;
- `medium`;
- `high`.

Для уведомлений по правилам важность берётся из соответствующего правила F8. Для недоступности хоста используется `high`.

## 4. Ручное решение уведомления

`POST /api/alerts/{id}/resolve`

Назначение: вручную отметить активное уведомление решённым.

Успешный ответ: HTTP `200 OK`

```json
{
  "ok": true
}
```

После решения:
- `status` становится `resolved`;
- `resolved_at` получает время решения.

Если уведомление не найдено, возвращается HTTP `404 Not Found`.

Если уведомление уже решено, повторный запрос не должен создавать ошибку или дублировать действие.

## 5. Автоматическая проверка

Проверка выполняется каждые 10 секунд.

### Проверка правил F8

1. Получить включённые правила.
2. Получить последние метрики соответствующих хостов.
3. Сравнить значения с порогами правил.
4. Если условие нарушено — создать уведомление со статусом `firing`.
5. Если условие больше не нарушено — перевести соответствующее активное уведомление в `resolved`.

Для одной пары `host_id + rule_id` допускается только одно активное уведомление.

Если уведомление было вручную решено, оно не должно создаваться заново, пока соответствующее условие не перестанет выполняться. Новое уведомление допускается при следующем нарушении после восстановления показателя.

### Проверка доступности хостов

Если `last_seen_at` хоста старше 30 секунд:
- создать уведомление `kind = offline`;
- установить `status = firing`;
- не создавать дубликаты активного уведомления для этого хоста.

Когда хост снова начинает отправлять данные:
- перевести активное offline-уведомление в `resolved`;
- заполнить `resolved_at`.

## 6. Хранение данных

Используется существующая таблица `alerts`.

Поля таблицы:
- `id`;
- `host_id`;
- `rule_id`;
- `kind`;
- `status`;
- `message`;
- `started_at`;
- `resolved_at`.

Дополнительные поля `host_name` и `severity` в ответе API могут формироваться Backend на основе связанных таблиц `hosts` и `alert_rules`. Добавлять их в таблицу `alerts` не требуется.

Каждое новое срабатывание создаёт отдельную запись. Решённые уведомления сохраняются для истории.

## 7. Ошибки

Все ошибки возвращаются в общем формате проекта.

Пример:

HTTP `404 Not Found`

```json
{
  "error": {
    "code": "not_found",
    "message": "Alert not found"
  }
}
```

## 8. Зависимости

- F6 предоставляет метрики и время последней активности хостов.
- F8 предоставляет включённые правила мониторинга.
- F14 использует эти данные для формирования уведомлений.

F14 не собирает метрики самостоятельно и не создаёт правила мониторинга.
